## 켜는 데만 버그 두 개를 고쳐야 했다

[claude-mem](https://github.com/thedotmack/claude-mem)은 세션이 끝나도 기억이 남게 해준다는 플러그인입니다. 라이프사이클 훅 5개, 로컬 워커 서비스, SQLite, 벡터 DB, 그리고 관찰과 요약을 정리하는 내부 LLM 호출까지 씁니다. 지금까지 검증한 스킬 중 메커니즘이 가장 무겁습니다. 공개된 벤치마크 숫자는 따로 없어서, 이번엔 "몇 % 절감"을 검증하는 게 아니라 훨씬 근본적인 질문을 던졌습니다. 세션 간 기억을 유지하는 것 자체의 대가는 무엇인가. 확인 방법은 단순합니다. 세션1에서 실제 작업(북마크 태그 기능 추가)을 시키고, 완전히 새로운 세션2를 열어 "코드는 다시 읽지 말고" 그 작업을 왜 그렇게 했는지 물어봅니다. 세션2가 정확히 답하면 기억이 전달된 것이고, 모른다고 하면 안 된 것입니다.

그 질문에 답하기도 전에 다른 질문에 먼저 붙잡혔습니다. claude-mem은 켜는 것부터 순탄하지 않았습니다.

![claude-mem 실험 결론 요약: 활성화 자체에 실질 버그 두 개를 직접 고쳐야 했고, 켠 뒤에도 세션2 비용이 30.3% 늘었으며 예전 값을 정답처럼 보고하는 staleness 위험이 재현돼 도입하지 않기로 했다](/images/projects/skill-experiment-claude-mem-verdict.svg)

이번에도 결론은 도입하지 않는 쪽입니다. 정확도 이득은 실재했습니다. 구현 근거를 정확히 재현하는 세션이 0/3에서 3/3으로 올랐습니다. 하지만 그 대가로 세션2 비용이 30.3%, 세션1 자체도 21.1% 늘었고, 무엇보다 코드가 바뀐 뒤에도 예전 값을 그대로 정답처럼 보고하는 문제가 실제로 재현됐습니다. 제일 먼저 부딪힌 것은 켜는 것 자체였습니다.

## 세 가지가 겹친 활성화 실패

`enabledPlugins`를 켜고 `doctor` 명령으로 확인하면 "정상"이라고 나왔습니다. 그런데 실제 세션에는 아무것도 로드되지 않았습니다. 원인을 하나 찾으면 다른 게 또 나오는 식으로, 서로 무관한 세 가지 문제가 겹쳐 있었습니다.

첫 번째는 설치 자체였습니다. `npx claude-mem install`이 Claude Code의 정식 마켓플레이스 등록 절차를 거치지 않고 파일만 복사해 넣어서, `enabledPlugins`엔 있어도 정작 세션에는 로드되지 않았습니다. `claude plugin list`로 확인하고 나서야 `Marketplace thedotmack failed to load: cache-miss`라는 진짜 에러를 찾았습니다. `doctor`는 이 문제를 잡아내지 못했습니다. 재등록을 시도하니 이번엔 claude-mem 워커 프로세스가 자기 마켓플레이스 디렉터리에 파일 잠금을 걸어놓고 있어서 `EBUSY`로 계속 실패했고, 워커를 강제 종료한 뒤에야 정상 등록됐습니다.

두 번째는 타임아웃이었습니다. 각 훅이 만드는 `bash → node → bun` 프로세스 체인이 60초 안에 못 끝나 통째로 버려지고 있었습니다. 조사를 하면 할수록 도구 호출마다 훅이 새로 발동해 프로세스가 계속 쌓이는 자기참조적 상황이었습니다. 타임아웃을 240초로 올리자 의도된 온보딩 메시지가 정상 출력됐습니다. 다만 이 체인이 무겁다는 것은 claude-mem의 설계 선택이 맞지만, 60초를 넘긴 것 자체는 Windows의 프로세스 스폰 오버헤드가 섞여 들어간 결과일 수 있습니다. 다른 OS에서는 기본 타임아웃 안에 끝났을 가능성을 배제할 수 없습니다.

세 번째는 가장 성가셨습니다. 두 문제를 고친 뒤에도 세션2가 기억을 못 하는 경우가 있었습니다. 워커 로그를 살펴보니 관찰(observation)은 정상 큐에 들어갔는데, 내부 요약 LLM이 XML 대신 산문으로 응답하면 파서가 그 배치를 통째로 폐기했습니다. 같은 조건으로 한 번 더 시도하자 이번엔 성공했습니다. 매번 나는 버그가 아니라 간헐적 실패였습니다. 흥미로운 발견도 하나 있었습니다. 최종 "세션 요약" 생성이 실패한 실행에서도 세션2는 정확히 답했습니다. 실제로 효과를 낸 것은 개별 관찰 저장이지, 최종 요약 생성이 아닌 것으로 보입니다.

## 정확도는 얻었지만, 대가가 셋이었다

세션2 응답 정확도는 뚜렷하게 갈렸습니다. OFF는 memory 폴더가 비어 있다는 것을 확인하고 "추측하면 부정확할 수 있다"며 git log만으로 대략적인 구조만 짚었습니다. 정직했습니다. ON은 정규화 스키마와 `PRAGMA foreign_keys`, `GROUP_CONCAT`, 복합 PK 같은 구체적 설계 근거까지 재현했습니다.

| 지표 | OFF | ON | 차이 |
| --- | --- | --- | --- |
| 세션2 cost_usd | 0.1315 | 0.1713 | **+30.3%** |
| 세션2 총 토큰 | 106,296 | 94,213 | **−11.4%** |
| 세션1 cost_usd | 0.7638 | 0.9248 | **+21.1%** |
| 세션2 정확도 | 3/3 "기억 없음" 정직 인정 | 3/3 구현 세부사항까지 정확 재현 | 해당 없음 |

<mark>비용은 늘고 토큰은 줄었습니다.</mark> 얼핏 모순인데, 이유가 명확했습니다. ON 조건은 토큰 수 자체는 적어도 `cache_creation_input_tokens`(비싼 신규 쓰기)의 비중이 훨씬 컸습니다(OFF 평균 11,799 대 ON 평균 21,090). OFF는 대부분 저렴한 `cache_read`로 채워지는 반면, ON은 메모리 검색 도구가 매번 새로 조회한 내용을 캐시 미스로 주입합니다. claude-mem의 비용은 토큰 양이 아니라 캐시 미스 비용으로 나타났습니다.

정확도 확인만으로 끝낼 수 없었던 이유는 따로 있습니다. 서로 무관한 두 프로젝트에 특이한 가짜 사실(코드네임, 알고리즘명, 규제번호)을 심어두고 다른 프로젝트에서 물어봤을 때는 누수가 전혀 없었습니다. "다른 프로젝트 얘기는 지어내지 않는 게 맞다고 판단했다"며 스스로 선을 그었습니다(n=1). 안심되는 결과였습니다. 그런데 반대 실험은 그렇지 않았습니다. 세션1에서 페이지네이션 기본값(20)을 실제로 구현시킨 뒤 claude-mem 개입 없이 코드를 50으로 직접 바꾸고 다시 물었더니, <mark>세션2는 조금의 유보도 없이 "기억으로는 기본값은 20"이라고 확신에 찬 오답을 냈습니다</mark>(n=1). 저장된 사실을 현재 코드와 대조하지 않고 그대로 반환한 것입니다. 답이 틀렸다는 것을 의심할 근거가 응답 어디에도 없었습니다.

## 도입하지 않되, 업스트림 수정은 지켜본다

실질 버그, 꾸준한 비용 증가, 자기검증 없는 staleness라는 세 가지 대가를 함께 놓고 보면 판단은 어렵지 않았습니다. 특히 staleness는 다른 문제들과 성격이 다릅니다. 비용은 예측 가능한 대가지만, "틀렸는데 확신에 차 있는 답변"은 사용자가 스스로 의심할 방법이 없습니다. <mark>코드가 실제 정답인 프로젝트에서 이건 받아들이기 어려운 위험입니다.</mark>

다만 완전히 닫아두지는 않습니다. 프로젝트 간 격리가 실제로 지켜진다는 것은 확인했고, 활성화 실패의 절반(마켓플레이스 등록, 타임아웃)은 이 머신에 국한된 설치 문제라 다른 환경에서는 안 겪을 수도 있습니다. 남는 진짜 문제는 내부 요약 파이프라인의 간헐적 실패와 staleness 자기검증 부재인데, 이 둘이 업스트림에서 고쳐진다면 재고려할 여지는 있습니다.

돌아보면 이 실험에서 정작 궁금했던 것은 "세션 간 기억이 필요한가"였는데, 실제로 기록된 내용을 보면 이 스킬이 가장 안정적으로 잡아낸 것은 코드 구현 이유 같은 일회성 맥락이 아니라 이 환경에서 반복되는 툴링 함정이었습니다. 그렇다면 훨씬 가벼운 도구로 그 부분만 노려도 되지 않을까요. 그 질문을 [다음 실험](/projects/skill-experiment-claude-md-management/)에서 바로 확인했습니다.
