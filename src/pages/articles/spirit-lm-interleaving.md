## 목소리는 복제했다, 그런데 무슨 말인지는 모른다

[VALL-E 리뷰](/articles/valle-ar-nar-pipeline)에서 3초 프롬프트만으로 화자를 복제하는 것을 봤습니다. 인상적이지만 VALL-E가 하는 일은 정확히는 "이 목소리로 이 텍스트를 읽어라"는 지시를 정교하게 수행하는 것이지, 그 텍스트가 무슨 뜻인지 이해하고 반응하는 것과는 다릅니다. 목소리는 흉내 내지만 말의 의미를 이해하지는 못합니다. 대화하고, 질문에 답하고, 맥락을 유지하려면 텍스트 LLM이 가진 지능이 필요하다는 것이 4편이 남긴 숙제였습니다.

이 지능을 음성에 옮기는 가장 직관적인 방법은 기존 텍스트 LLM 앞뒤에 오디오 인코더와 디코더를 붙이는 것입니다. 그런데 이 방식은 대개 무겁습니다. 두 모달리티를 잇는 어댑터 모듈을 새로 설계해 학습시켜야 하고, 텍스트로 나타낸 뜻과 음성으로 나타낸 뜻이 같은 자리에 놓이도록 맞추는 별도의 학습 목표까지 더해야 하는 경우도 많습니다. 반대로 [AudioLM](/articles/audiolm-hierarchical-generation)처럼 음성 토큰만으로 처음부터 다시 학습시키면, 텍스트 LLM이 이미 갖고 있는 방대한 지식과 추론 능력을 통째로 버리고 시작하는 셈이 됩니다.

Meta가 공개한 **Spirit LM**의 답은 놀랄 만큼 단순했습니다. 어댑터도, 별도의 정렬 모듈도 없이 <mark>텍스트 토큰과 음성 토큰을 하나의 시퀀스 안에 단어 단위로 번갈아 끼워 넣고(interleaving), 그 시퀀스로 기존 텍스트 LLM을 이어서 학습</mark>시키는 것입니다. "the cat"이라는 텍스트 다음에 "sat on"에 해당하는 음성 토큰이 이어지고, 다시 "the mat"이라는 텍스트로 돌아오는 식입니다. 모델은 지금 자신이 텍스트를 읽고 있는지 음성을 듣고 있는지 구분할 필요조차 없습니다. 그냥 다음 토큰을 예측할 뿐입니다.

![Spirit LM의 텍스트-음성 인터리빙 다이어그램. Llama 2 7B를 웜스타트한 뒤, 텍스트 토큰 the·cat과 음성 토큰 Hu3·Hu7…Hu200과 다시 텍스트 토큰 the·mat이 단어 경계에서 번갈아 나타나는 하나의 토큰 시퀀스로 학습한다.](/images/articles/spirit-lm-interleaving.svg)

결과는 이 단순함을 정당화합니다. 의미 이해를 재는 Topic-StoryCloze 벤치마크에서, 음성 문맥에 음성으로 이어가는 조건의 정확도가 82.9%로, 이전 접근인 TWIST(76.4%)를 앞섭니다. 텍스트 문맥으로 음성을 잇거나(72.7%) 음성 문맥으로 텍스트를 잇는(88.6%) 교차 모달리티 조건에서도 무리 없이 작동합니다. 다만 이렇게 값싸게 지능을 옮긴 데는 값이 붙습니다. 저자들은 텍스트 LLM이 원래 갖고 있던 능력을 얼마나 내줬는지를 <abbr title="새 모달리티를 얹은 대가로 텍스트 전용 모델 대비 성능이 떨어지는 현상" tabindex="0">modality tax</abbr>라는 이름으로 직접 수치로 공개합니다.

## 지능을 옮기는 데 드는 진짜 비용

텍스트 LLM의 지능을 음성으로 옮기려는 이전 접근들은 저마다 비용을 치렀습니다. [AudioLM](/articles/audiolm-hierarchical-generation)이나 GSLM 계열처럼 음성 토큰만으로 처음부터 학습시키면, 텍스트 LLM이 대규모 코퍼스에서 이미 습득한 문법과 상식, 추론 능력을 전혀 물려받지 못한 채 다시 배워야 합니다. ASR로 텍스트를 뽑고 LLM으로 답을 만든 뒤 TTS로 다시 합성하는 cascade 방식은 [1편](/articles/prologue-why-speech-language-model)에서 짚었듯 감정과 억양 같은 정보가 텍스트를 거치며 소거되고, 세 단계를 거치며 지연이 쌓입니다. 텍스트와 음성 표현 공간을 잇는 어댑터를 새로 설계하면, 그 어댑터 자체가 별도의 학습 파이프라인과 손실 함수를 요구하는 새로운 엔지니어링 비용이 됩니다.

Spirit LM 저자들이 던진 질문은 그래서 "어떤 어댑터를 설계할까"가 아니라, 모달리티를 잇는 구조를 아예 새로 만들지 않고 기존 언어모델의 다음 토큰 예측 능력만으로 두 모달리티를 붙일 수 있는가였습니다.

## 정렬도, 어댑터도 없이 그냥 섞는다

#### 단어 경계에서 무작위로 모달리티를 전환한다

정렬된 음성-텍스트 병렬 코퍼스에서, 각 학습 스텝마다 단어 경계 지점을 무작위로 골라 텍스트 구간과 음성 구간을 전환합니다. `[Text] the cat [Speech][Hu3][Hu7]..[Hu200][Text] the mat`처럼, 음성 토큰 구간이 "sat on"이라는 텍스트에 대응하는 식입니다. 모델 입장에서는 특별한 스위치나 게이트가 필요 없습니다. 시퀀스의 다음 토큰이 어느 모달리티에 속하든 그냥 예측하기만 하면 됩니다.

#### 텍스트 LLM을 웜스타트해서 이어 학습한다

Spirit LM은 처음부터 학습하지 않습니다. **Llama 2 7B**의 사전학습 가중치에서 시작해 <abbr title="완전히 새로 학습하는 대신 이미 학습된 모델의 가중치에서 이어서 학습을 시작하는 방식" tabindex="0">warm-start</abbr>로 지속 사전학습을 진행합니다. 음성 토큰은 HuBERT 기반으로 얻은 501개 어휘의 semantic unit이고, 중복 토큰은 제거해 시퀀스를 압축합니다. 학습 데이터는 음성 전용 458K시간(28.2B 토큰), 텍스트 전용 307B 토큰, 그리고 정렬된 음성과 텍스트 병렬 데이터 111K시간(음성 7B에 텍스트 1.4B 토큰)을 약 33.3%씩 균형 있게 섞습니다.

#### Expressive 버전은 트랙을 두 개 더 얹는다

Base 버전은 "무슨 말인지"만 담는 HuBERT semantic 토큰 한 종류만 사용합니다. Expressive 버전은 여기에 두 가지를 더 얹습니다. 하나는 목소리의 높낮이를 담는 피치 토큰이고, 다른 하나는 말투 전체를 담는 스타일 토큰입니다. 피치 토큰은 목소리의 기본 주파수를 양자화해 얻고, 스타일 토큰은 억양과 리듬을 1초 단위로 요약한 뒤 화자마다 다른 개성을 걷어내어 만듭니다. 세 토큰은 뽑아내는 주기가 초당 25개, 12.5개, 1개로 서로 다르지만, 각 토큰이 몇 초 지점에 해당하는지 표시돼 있어서 그 순서대로 늘어놓으면 하나의 시퀀스로 합쳐집니다. [2편](/articles/speech-tokens-two-families)에서 다룬 semantic 토큰만으로는 담기지 않던 감정과 억양을, 텍스트를 거치지 않고 되살리려는 시도입니다. cascade 파이프라인에서는 텍스트로 바뀌는 순간 사라졌을 억양 정보가, 여기서는 처음부터 텍스트로 변환되지 않고 별도 트랙으로 나란히 흐릅니다.

![Spirit LM Expressive의 세 토큰 트랙 병합 다이어그램. HuBERT semantic 트랙(25Hz), 피치 트랙(F0를 VQ-VAE로 양자화, 12.5Hz), 스타일 트랙(1Hz)은 샘플링 레이트가 서로 다르지만, 각 토큰에 붙은 타임스탬프 순으로 정렬하면 하나의 토큰 시퀀스가 된다. Base는 HuBERT 트랙만 쓰고, Expressive는 피치와 스타일 트랙을 더해 세 트랙을 함께 쓴다.](/images/articles/spirit-lm-expressive-tracks.svg)

## 값싸게 옮긴 지능에 매겨지는 대가

얻은 것은 별도 설계 없이 확보한 의미 이해입니다. Topic-StoryCloze 음성에서 음성 정확도는 82.9%로, 같은 조건의 TWIST(76.4%)를 앞서는 수치입니다. 텍스트 문맥과 음성 문맥을 서로 넘나드는 교차 모달리티 조건(텍스트에서 음성 72.7%, 음성에서 텍스트 88.6%)에서도 자연스럽게 이어갑니다. 별도 어댑터나 정렬 목적함수 없이, 그냥 시퀀스를 섞고 이어 학습시키는 것만으로 이만큼의 의미 이해가 확보됐다는 것 자체가 이 접근의 핵심 성과입니다. 다만 ASR과 TTS로 구성한 <abbr title="음성 인식·언어모델·음성합성을 순차적으로 연결한 파이프라인" tabindex="0">cascade</abbr> 상한선(94.76%)에는 아직 못 미칩니다.

잃은 것은 텍스트 능력에 매겨진 modality tax입니다. 저자들은 <mark>텍스트 전용 Llama 2 대비 성능 저하를 스스로 언급</mark>합니다. 텍스트 모드에서 SpiRit-LM은 어휘 판별(WUGGY) 80.3, 문법성 판단(BLIMP) 73.3, StoryCloze 79.4를 기록하는데, 저자들은 이 세 지표 모두 Llama 2 대비 "2포인트 미만"의 저하라고 밝힙니다. 그런데 MMLU(5-shot) 점수는 36.9% 수준으로 훨씬 크게 떨어집니다. 음성 모달리티를 얹는 대가로 텍스트 전용 모델의 폭넓은 지식 활용 능력이 눈에 띄게 희생된 것입니다. Expressive 버전은 피치와 스타일 트랙까지 더해 시퀀스가 길어지는 만큼 Base 버전보다 더 저하됩니다.

소량 학습 태스크는 아직 실용 수준이 아닙니다. 10-shot으로 파인튜닝한 ASR의 <abbr title="Word Error Rate: 음성 인식 결과와 정답 텍스트 사이의 단어 단위 오류율" tabindex="0">WER</abbr>은 LibriSpeech Clean 기준 21.9%, TTS의 문자 오류율(CER)은 45.5%입니다. 전용으로 학습된 ASR과 TTS 모델과 비교하면 아직 거리가 있는 수준입니다.

## 병목은 인터리빙이 아니라 토크나이저에 있다

cascade와의 격차는 토크나이제이션 자체의 정보 손실에서 옵니다. 저자들은 이 격차의 원인을 명확히 짚습니다. "음성 토크나이제이션은 Whisper ASR 대비 정보 손실을 일으킨다." 곧 interleaving 방식 자체의 한계가 아니라, 음성을 HuBERT 유닛으로 이산화하는 단계에서 이미 일부 정보가 사라진다는 뜻입니다. 실무팀이 이 접근을 도입한다면, 병목이 인터리빙 학습 방식이 아니라 토크나이저 품질에 있다는 것을 먼저 짚어야 합니다. 그래야 개선 투자를 어디에 넣을지 판단이 섭니다.

MMLU 하락폭은 텍스트 추론이 필요한 기능에 예산으로 반영해야 합니다. 음성 인터페이스를 얹으면서 텍스트 전용 모델 대비 MMLU가 이만큼 떨어진다는 것은, 이 모델에 복잡한 지식 기반 질의응답이나 다단계 추론을 기대하는 서비스를 얹을 때는 그 성능 저하를 사전에 별도로 측정하고 예산에 반영해야 한다는 뜻입니다. "음성으로도 텍스트만큼 똑똑하다"는 주장은 이 수치 앞에서 조심스럽게 받아들여야 합니다.

warm-start는 자체 도메인 음성모델의 진입 장벽을 낮춥니다. 처음부터 음성 언어모델을 학습시키려면 막대한 컴퓨팅과 데이터가 필요합니다. Spirit LM처럼 이미 검증된 텍스트 LLM 가중치에서 지속 사전학습으로 시작하는 경로는, 자체 도메인 음성 모델을 시도해보려는 팀에게 훨씬 낮은 비용의 진입점이 됩니다. "기존 지능 위에 모달리티를 얹는다"는 이 전략은 이후 등장하는 여러 음성 대화 모델이 똑같이 따르는 출발점이기도 합니다.

그리고 텍스트 LLM의 위험도 그대로 상속됩니다. 논문은 "사전학습된 모든 기반 모델과 마찬가지로 Spirit LM도 유해한 콘텐츠를 생성할 수 있다"고 인정합니다. 웜스타트가 텍스트 LLM의 능력만 물려주는 게 아니라 그 위험까지 그대로 상속한다는 뜻입니다. 음성 인터페이스를 얹는다고 안전성 문제가 새로 생기는 게 아니라, 이미 있던 문제가 새로운 출력 형태(음성)로 표출될 뿐이라는 것을 배포 전에 짚어야 합니다.

## 구조를 바꾸기 전에 시퀀스를 섞어봐라

복잡한 정렬 메커니즘이나 전용 어댑터를 설계하는 대신, 데이터를 섞는 방식만 바꿔서 문제를 우회했다는 것이 가장 인상적인 지점입니다. 모델 구조를 손대지 않고 입력 시퀀스의 구성 방식만 바꾸는 것으로 새로운 능력을 끌어낼 수 있습니다. 여러 모달리티나 여러 데이터 소스를 하나의 모델에 결합해야 할 때, 새 아키텍처를 설계하기 전에 "그냥 같은 시퀀스에 섞어서 이어 학습시키면 안 되는가"부터 물어볼 만합니다.

그리고 MMLU 36.9%라는, 결코 좋아 보이지 않는 숫자를 저자들이 그대로 공개했다는 점도 눈여겨볼 만합니다. 새로운 능력을 값싸게 얻었다고 자랑하는 논문일수록, 그 대가를 구체적인 숫자로 함께 보여줄 때 그 결과를 믿을 수 있습니다.

이해하고 생성하는 것까지는 됐습니다. 그런데 텍스트를 다 만들고 나서야 음성을 시작하는 구조라면, 응답이 오기까지 몇 초가 그대로 걸립니다. [다음 리뷰](/articles/low-latency-streaming-triangle)는 이 지연을 줄이려는 세 가지 접근을 나란히 비교합니다.
