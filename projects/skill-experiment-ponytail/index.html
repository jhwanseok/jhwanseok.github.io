[스킬은 켜봐야 안다 #1] 토큰이 준다는 스킬, 진짜였을까: ponytail을 켜고 끄며 검증하다

“토큰이 준다”는 벤치마크, 그대로 믿어도 될까

ponytail은 Claude가 “게으른 시니어 개발자”처럼 굴게 만드는 스킬입니다. YAGNI를 강제해서 굳이 필요 없는 추상화를 피하고, 새 라이브러리나 커스텀 컴포넌트 대신 표준 라이브러리와 네이티브 기능을 우선하도록 유도합니다. 저자가 공개한 자체 벤치마크(tiangolo/full-stack-fastapi-template 기준, Haiku 4.5)는 코드량 약 54% 감소, 토큰 사용량 약 22% 절감을 주장합니다. 숫자는 인상적이지만, 벤치마크는 대부분 저자 자신이 설계하고 저자 자신이 측정한다는 근본적인 한계가 있습니다. 내가 실제로 쓰는 코드베이스에서도 같은 효과가 날까요, 아니면 특정 시나리오에 맞춰진 숫자일까요.

이 질문에 “그럴듯하다”거나 “의심스럽다”로 답하고 싶지 않았습니다. 그래서 직접 켜고 꺼가며 같은 작업을 반복 실행해 비교해보기로 했습니다.

실험을 마친 지금, 저는 이 스킬을 상시로는 켜지 않습니다. 벤치마크 숫자를 못 믿어서가 아닙니다. “동일 품질에 더 단순한 대안이 있는가”라는 분기점이 있는 작업에서는 LOC가 34~49% 줄어드는 효과가 이번 실험에서도 그대로 나타났습니다(티켓별로 −34.4%, −49.2%). 문제는 그 분기점에 걸리는 작업 자체가 제 일에서 큰 비중이 아니라는 것입니다. 저는 Python 기반 AI 개발과 이 블로그 같은 글쓰기를 주로 하는데, 글쓰기는 애초에 코드 생성이 아니라 ponytail이 개입할 지점 자체가 없고, Python 개발에서도 “새 패키지를 추가할지 직접 짧게 구현할지” 고민하는 순간이 아예 없지는 않지만 늘 나오는 것도 아닙니다. 가장 먼저 걸린 것은 티켓 선택이었습니다.

직접 확인하는 과정에서 두 번 길을 잘못 들었다

벤치마크 숫자를 재현해보려면 최소한의 조건이 있었습니다. 같은 작업을 스킬을 껐을 때와 켰을 때 각각 여러 번 실행해서 비교할 수 있어야 하고, 그 비교에 스킬 자체가 아닌 다른 변수(이전 실행의 잔여 상태, 다른 스킬의 개입)가 섞여 들면 안 됐습니다. 그래서 skill-experiment-lab이라는 재사용 가능한 하네스를 만들었습니다. fixtures/bookmarks-api처럼 archetype별 baseline 앱을 git 태그로 고정해두고 이후 어떤 실험에서도 그 태그 자체는 건드리지 않으며, 스킬을 검증할 때마다 그 태그에서 격리된 worktree를 OFF와 ON 두 개 새로 만들어 같은 티켓을 실행합니다. 지표는 Agent(isolation: "worktree")가 기계적으로 반환하는 subagent_tokens, tool_uses, duration_ms를 그대로 쓰기로 했습니다. 계측 스크립트를 따로 만들면 그 스크립트 자체가 오류의 원인이 될 수 있어서입니다. ponytail은 “코드 생성/볼륨” archetype으로 분류했고, 1차 지표는 subagent_tokens 평균(n=3), 2차 지표로 tool_uses와 git diff --stat 기준 LOC를 함께 보기로 했습니다.

첫 번째로 잘못 든 길은 티켓 선정이었습니다. “북마크에 태그 추가 그리고 GET /bookmarks?tag=... 필터링”이면 조인 테이블이냐 JSON 컬럼이냐 같은 구현 선택지가 있어 보여서 괜찮은 테스트라고 판단했습니다. 그런데 1차 실행 결과, OFF와 ON의 코드량과 토큰이 거의 같았습니다. 무언가 이상해서 ponytail 저자 자신의 벤치마크 데이터를 다시 들여다보니, 순수 CRUD 티켓(“제목으로 검색”)은 저자 벤치마크에서도 44줄에서 44줄로 차이가 0%였습니다. 효과가 실제로 나타난 사례는 date picker(404줄에서 23줄, −94%)나 color picker(287줄에서 23줄, −92%)처럼 라이브러리를 새로 설치하는 대신 네이티브 기능으로 대체할 수 있는 지점이 있는 티켓들이었습니다. 내가 고른 티켓에는 애초에 그런 분기점이 없었던 것입니다. date picker 케이스를 본떠 “북마크에 선택적 remind_at 리마인드 날짜 추가, 생성과 수정 화면에 picker 포함”이라는 두 번째 티켓을 새로 만들었습니다.

두 번째로 잘못 든 길은 더 근본적이었습니다. 두 티켓 모두 1세대 ON 결과를 받아들고 나니 무언가 미심쩍었습니다. OFF와 별 차이가 없었습니다. 진단 세션을 5번 돌려보고 나서야 이유를 알았습니다. enabledPlugins.ponytail@ponytail을 전역 설정에서 켜는 것과, 실제로 서브에이전트가 그 룰셋을 받는 것은 별개의 일이었습니다. 설정값은 정상적으로 전달됐지만, 룰셋 텍스트 자체는 5회 진단 모두에서 주입되지 않았습니다. isolation: "worktree" 옵션 여부와도 무관했습니다. 곧 1세대 ON 데이터는 사실상 OFF와 OFF를 비교하고 있었던 셈입니다. 우회책은 프롬프트에서 Skill 도구로 ponytail:ponytail을 명시적으로 호출하게 만드는 것이었습니다. 이렇게 하니 실제 룰셋(“ACTIVE EVERY RESPONSE” 문구, 7단계 판단 사다리)이 로드됐고, 이 조건(ON-v2)으로 두 티켓을 다시 돌렸습니다. 이 발견은 skill-experiment-lab의 CLAUDE.md에 “훅 기반 플러그인 실험 전 활성화 검증 필수” 원칙으로 남겨뒀고, 이후 superpowers와 caveman 실험에도 그대로 이어졌습니다.

두 실패는 성격이 달랐지만 교훈은 같았습니다. 설계가 그럴듯해 보여도, 실제로 걸리는지는 직접 파고들어야 알 수 있었습니다.

줄어든 건 코드였지, 토큰이 아니었다

OFF와 ON-v2를 나란히 놓고 봤을 때 가장 먼저 든 생각은 “예상과 다르게 갈렸다”는 것이었습니다. 코드가 준 만큼 토큰도 줄 거라고 막연히 기대했는데, 이 둘은 서로 다른 이야기였습니다. LOC는 두 티켓 모두 뚜렷하게 줄었지만(−49.2%, −34.4%), 토큰은 줄기는커녕 티켓 B에서는 오히려 늘었습니다(+8.7%).

티켓 지표 OFF ON-v2 차이
A (태그+필터링) subagent_tokens 52,724 53,126 +0.8%
A tool_uses 22.0 20.7 −6.1%
A LOC 추가 175.3줄 89.0줄 −49.2%
B (리마인드 날짜) subagent_tokens 49,244 53,533 +8.7%
B tool_uses 24.7 22.7 −8.1%
B LOC 추가 154.3줄 101.3줄 −34.4%

토큰이 왜 안 줄었는지 더 들여다보니, ON-v2 세션은 Skill 도구로 SKILL.md(6,757자, 약 1,5002,000토큰 추정)를 매번 로드하는 고정 비용을 진다는 것을 감안해야 했습니다. 이 로딩 비용을 빼고 순수 작업 토큰만 추정해보면, 티켓 A는 오히려 23% 줄어 있었습니다. 로딩 비용이 절감분을 가리고 있었던 것입니다. 티켓 B는 그래도 +4.7~+5.7%가 남았는데, 이건 ponytail이 스스로 밝힌 부작용, 곧 모델이 판단 사다리를 곱씹느라 생각 토큰을 더 쓸 수 있다는 패턴과 맞아떨어졌습니다.

숫자보다 실제 diff에서 드러난 행동 차이가 더 인상적이었습니다. 티켓 A에서 ON-v2 세션 3개 중 2개는 태그를 조인 테이블이 아니라 콤마로 이어붙인 문자열 컬럼으로 저장했습니다(OFF는 6개 세션 모두 조인 테이블). 나머지 하나는 조인 테이블을 택했지만 “동일 비용이면 더 정확한 쪽을 택한다”는 ponytail 자신의 규칙을 근거로 명시적으로 정당화했습니다. 티켓 B에서는 ON-v2 세션 3개 중 2개가 remind_at 필드만 건드리는 좁은 PATCH 엔드포인트를 만들고 “일반 수정 엔드포인트는 생략, 필요할 때 추가”라고 코멘트로 남겼습니다. OFF는 전 필드를 교체하는 범용 PUT을 만들었습니다. 숫자로는 안 보이던 “판단의 흔적”이 코드에는 남아 있었습니다.

이 결과를 어디까지 믿어야 할지도 같이 정리해야 했습니다. 효과가 나타나려면 “동일 품질에 더 단순한 대안이 있는가”라는 분기점이 있어야 한다는 것이 이번 실험이 확인한 핵심 조건이고, 그 분기점이 없었던 첫 번째 시도(순수 CRUD 티켓)에서는 효과가 거의 없었습니다. 이는 ponytail 저자 자신의 벤치마크와도 일치합니다. 표본 크기(n=3, 티켓 2개)도 작고, 저자의 벤치마크(Haiku 4.5에 티켓 12개)보다 더 강한 모델로 실험했다는 점도 감안해야 합니다. 저자 스스로도 강한 모델일수록 격차가 줄어든다고 인정합니다. 토큰 분해가 사후 추정이라는 점도 마찬가지입니다. 다른 변수는 모두 통제한 채 진행했습니다.

효과가 아니라 빈도를 본다

가장 크게 바뀐 것은 스킬을 도입할지 판단하는 방식입니다. 이제는 “이 스킬이 몇 % 절감한다더라”는 숫자를 그대로 믿거나 의심하는 대신, 내가 실제로 하는 작업에서 그 스킬이 개입할 지점이 얼마나 자주 나오는지부터 확인합니다. 제 작업은 크게 둘로 나뉩니다. 이 블로그 같은 글쓰기는 코드 생성이 아니라 애초에 ponytail의 범위 밖이고, Python AI 개발에서는 “패키지를 새로 추가할지 직접 구현할지” 고민하는 순간이 가끔 있지만 매 작업마다 나오지는 않습니다. 그래서 결론은 “효과가 없다”가 아니라 “효과는 있는데, 걸리는 빈도가 낮아서 상시로는 안 켜둔다”입니다.

ponytail은 코드 생성 과정에서 표준 라이브러리 대신 커스텀 구현으로 손이 가려는 경향을 줄이는 데는 확실히 효과가 있었습니다. 그래서 상시로 켜두는 대신, 새 의존성을 추가할지 직접 구현할지를 자주 저울질해야 하는 작업, 예컨대 새 프레임워크로 이것저것 붙여보는 프로토타이핑이나 프런트엔드 컴포넌트를 고르는 작업을 할 때는 의도적으로 켜서 쓰는 것을 추천합니다.

더 오래 남을 습관은 따로 있습니다. 전역 설정에서 플러그인을 켰다고 해서 서브에이전트에 실제로 룰셋이 전달됐는지는 별개의 문제라는 것을, 숫자가 이상하게 나온 뒤에야 진단해서 알게 됐습니다. 앞으로 훅 기반 플러그인을 실험할 때는 이 활성화 검증을 먼저 하지 않으면, 실험 전체가 “OFF 대 OFF”를 비교하고 있으면서도 그 사실을 모를 수 있습니다.
