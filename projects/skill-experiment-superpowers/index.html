강제하지 않아도 스스로 판단해서 스킬을 부를까

superpowers는 using-superpowers라는 메타 스킬을 통해, 상황에 맞는 세부 스킬(systematic-debugging, test-driven-development 등)을 명시적으로 호출하지 않아도 스스로 판단해서 부른다고 주장합니다. ponytail 실험에서 “설정에서 켰다고 실제로 켜진 것이 아닐 수 있다”는 것을 배운 뒤라, 이번에는 질문 자체가 달랐습니다. 토큰이 주는지가 아니라, 강제 없이도 정말 자발적으로 활성화되는지를 확인하고 싶었습니다.

이 질문은 검증하기가 까다롭습니다. “너는 디스패치된 서브에이전트가 아니니 규칙을 따르라”고 프롬프트에서 코칭해버리면 결론을 미리 정해놓고 확인하는 꼴이 됩니다. 그렇다고 아무 장치 없이 두면, superpowers의 SUBAGENT-STOP 메커니즘(“서브에이전트로 디스패치된 경우라면 이 스킬을 무시하라”는 지침) 때문에 애초에 검증 자체가 성립하지 않을 수도 있습니다. 결국 이 문제를 어떻게 설계해서 풀었는지가, 결과 숫자만큼이나 이 실험의 핵심입니다.

두 번의 실험 끝에 저는 이 스킬을 도입하지 않기로 했습니다. 근본 원인을 맞히는 정확도는 쉬운 버그 하나와 하루 뒤 일부러 더 어렵게 설계한 버그 하나, 두 경우 모두에서 on/off 차이가 없었습니다. 강제나 코칭 없이도 스스로 systematic-debugging을 호출하는 비율은 버그가 어려울수록 오히려 더 높아졌지만(2/3에서 3/3으로), 그 프로세스 개선이 결과물 품질로 이어지는 증거는 두 실험 어디에서도 찾지 못했습니다. 대가는 두 실험 모두 일관되게 비용 +42~43%였습니다. 가장 까다로웠던 것은 검증 방법 자체를 설계하는 일이었습니다.

검증 방법을 다시 설계했다

강제로 systematic-debugging을 호출시키거나, “너는 디스패치된 서브에이전트가 아니다”라고 프롬프트에서 코칭하는 방법은 처음부터 제외했습니다. 전자는 “강제로 시키면 그 스킬 하나가 도는지”만 확인할 뿐 전체 체인이 스스로 판단해서 발동하는지는 보여주지 못하고, 후자는 모델의 결론을 프롬프트가 먼저 유도해버리는 셈이라 검증이라 부르기 어려웠습니다.

그래서 에이전트 아키텍처에 대한 메타 언급을 전부 지우고, 순수하게 1인칭 버그 리포트로만 티켓을 썼습니다. 이 요청이 “서브에이전트로 디스패치된 것”인지 아닌지는 모델이 스스로 판단하게 둔 것입니다. 가장 정직한 설계라고 생각했는데, 진단 단계에서 더 근본적인 문제가 드러났습니다. Agent(isolation: "worktree") 경로에서는 superpowers가 스킬 카탈로그에 아예 존재하지 않았습니다. Skill 도구로 명시 호출해도 Unknown skill이 반환됐습니다. ponytail에서 봤던 “설정은 됐는데 룰셋만 안 실린” 문제보다 더 심각한, 아예 도달 자체가 안 되는 실패였습니다.

그래서 최종 설계로 Agent 도구를 완전히 버리고, git worktree add로 직접 만든 worktree에서 헤드리스 claude -p "<티켓>" --output-format json --permission-mode bypassPermissions를 실행하는 방식으로 전환했습니다. 이건 진짜 최상위 세션이라 SUBAGENT-STOP이 애초에 적용될 근거가 없습니다. 지표는 CLI가 반환하는 JSON의 usage, total_cost_usd, duration_ms, num_turns를 그대로 파싱했는데, 이는 skill-experiment-lab의 “별도 계측 스크립트를 만들지 않는다”는 원칙에 대한 명시적 예외로 기록해뒀습니다. 사전 스모크 테스트로 OFF에는 using-superpowers 흔적이 전혀 없고 ON에는 SUBAGENT-STOP 문구를 포함한 전체 본문이 실제로 로드된다는 것, 로딩 비용만큼 cache_creation_input_tokens가 7,378에서 9,350으로 늘어난다는 것도 확인했습니다.

이 채택안으로 실행할 버그도 같이 정했습니다. bookmarks-api-baseline 태그에서 새 태그 bookmarks-api-baseline-bug를 만들고, GET /bookmarks?sort=title을 COLLATE NOCASE 없는 ORDER BY title로 구현해뒀습니다. 대문자로 시작하는 제목이 항상 소문자 제목보다 앞에 오는 전형적인 SQLite 대소문자 정렬 버그이고, 재현 테스트는 의도적으로 넣지 않았습니다. 티켓 텍스트는 OFF와 ON 동일하게, 아키텍처 언급 없는 순수한 1인칭 버그 리포트로 썼고, 마지막에 “어떤 접근을 택했는지, 어떤 스킬을 왜 썼는지 알려달라”는 자기 보고 요청으로 끝맺었습니다.

이렇게 확정한 실험 설계를 정리하면 이렇습니다.

항목 내용
검증 대상 superpowers (using-superpowers 메타 스킬)
픽스처 bookmarks-api-baseline-bug (대소문자 정렬 버그, 재현 테스트 없음)
티켓 아키텍처 언급 없는 1인칭 버그 리포트, OFF/ON 동일
조건 OFF / ON (enabledPlugins.superpowers)
실행 방식 headless claude -p 최상위 세션, git worktree add로 격리
반복 조건당 n=3 (총 6세션)
정량 지표 cost_usd · duration_ms · num_turns · total_tokens
정성 지표 근본원인 정확도, RED→GREEN 커밋 분리 여부, 자발적 스킬 호출 여부

결과물은 같은데 과정이 갈렸다

OFF와 ON 여섯 세션을 나란히 놓고 보면 이상한 대칭이 보였습니다. 근본 원인을 맞히는 정확도는 완전히 같은데, 거기 이르는 과정은 완전히 달랐습니다.

세션 cost_usd duration_ms turns tokens 커밋 RED→GREEN 분리 호출된 스킬
OFF-1 0.3089 68,160 12 23,838 1 아니오 없음
OFF-2 0.3615 67,870 14 26,697 1 아니오 없음
OFF-3 0.3543 62,193 15 24,809 1 아니오 없음
ON-1 0.5074 88,002 18 36,887 2 예 systematic-debugging
ON-2 0.5779 105,035 22 38,713 1 아니오 systematic-debugging
ON-3 0.3837 71,719 14 28,470 1 아니오 인지했지만 의도적으로 생략

평균(n=3)으로 보면 cost_usd는 0.3416에서 0.4897로(+43.4%), duration_ms는 66,074에서 88,252로(+33.6%), num_turns는 13.7에서 18.0으로(+31.7%), total_tokens는 25,115에서 34,690으로(+38.1%) 늘었습니다. 근본 원인(COLLATE NOCASE 또는 동등한 수정)은 6/6 세션 모두 정확했고, 재현 테스트가 실제로 버그를 잡아내는지도 6/6 모두 통과했습니다. 여기까지는 숫자로도 결과물로도 차이가 없었습니다.

차이는 diff와 로그를 직접 열어봐야 보였습니다. ON-1은 “주입된 using-superpowers 훅이 버그 수정 요청에는 systematic-debugging을 먼저 요구하고, 이번 요청이 여기 해당한다고 판단했다”고 스스로 근거를 밝히며 RED 커밋(2e6d68f)과 fix 커밋(0c0b641)을 분리했습니다. ON-2는 근본원인, 패턴, 가설, 구현의 4단계 프로세스를 그대로 밟았지만 커밋은 하나로 합쳤습니다. 흥미로운 것은 ON-3입니다. 훅의 요구 조건을 인지했지만, “코드 두 곳만 읽으면 원인을 알 수 있을 만큼 단순해서 다단계 가설 검증은 과하다”고 스스로 판단해 의도적으로 건너뛰었습니다. 강제된 규칙을 기계적으로 따른 것이 아니라 판단을 거쳐 적용한 사례였습니다. OFF 3세션은 애초에 목록에 superpowers가 없었으므로 모두 한 번에 버그를 고쳤습니다.

이 결과를 어디까지 믿어야 할지도 같이 정리해야 했습니다. 이번에 심은 버그는 SQLite collation 문제라는, 단일 파일만 봐도 원인을 특정할 수 있는 비교적 쉬운 버그였습니다. 강한 모델은 프로세스 없이도 정답을 맞혔고, “과정이 정교해진다”는 효과가 “결과물이 더 좋아진다”는 효과로는 이어지지 않았습니다. systematic-debugging이 원래 겨냥하는 다중 컴포넌트 버그나, 그럴듯한 증상만 고치고 넘어가기 쉬운 버그였다면 결과가 달랐을까요. 이 질문은 다음 실험으로 미뤄두지 않고, 하루 뒤 바로 확인해보기로 했습니다. 그 밖에 n=3이라 1/3 같은 개별 비율은 안정적인 수치로 보기 어렵고, claude -p로 전환하면서 Agent 도구의 자동 계측을 포기해야 했으며, “과정이 개선됐다”는 최종 판단은 git log와 diff로 교차 검증했지만 일부는 세션의 자기 보고에 의존했습니다.

일부러 더 어려운 버그로 다시 확인했다

1차 실험 결과를 받아들고 나서 가장 마음에 걸렸던 것은 “버그가 너무 쉬웠다”는 것이었습니다. systematic-debugging이 실제로 겨냥하는 상황은 원인이 여러 컴포넌트에 걸쳐 있거나 그럴듯한 증상 수정에 빠지기 쉬운 경우인데, SQLite collation 문제는 파일 하나만 보면 끝나는 단일 원인이었습니다.

그래서 TOCTOU(check-then-act) 레이스를 새로 심었습니다. static/app.js에는 POST 전에 GET으로 중복 여부를 확인하는 클라이언트 사전 체크만 있고, 백엔드(db.py, main.py)에는 URL 유일성을 보장하는 장치가 전혀 없습니다. 버그 리포트(“빠르게 두 번 클릭하면 중복이 생긴다”)를 표면적으로 읽으면 프런트엔드에 디바운스나 버튼 비활성화만 추가해도 증상은 사라진 것처럼 보입니다. 진짜 수정은 서버와 DB 계층에 유일성을 강제하는 것입니다. 판정도 코드 리뷰의 주관적 판단에 맡기지 않았습니다. 브라우저를 거치지 않고 같은 URL로 POST를 연속 두 번 보내, 중복이 실제로 생기는지 직접 확인하는 방식으로 “증상만 고쳤는지 근본을 고쳤는지”를 객관적으로 판정했습니다.

지표 OFF ON 차이
cost_usd 0.4941 0.7016 +42.0%
근본 원인 수정(직접 API 검증) 3/3 3/3 차이 없음
스킬 자발 호출 자기보고 0/3 3/3 1차보다 강화

근본 원인, 곧 서버와 DB 계층의 유일성을 고친 세션이 OFF와 ON 모두 3/3이었고, “증상만 고침” 판정은 단 한 건도 없었습니다. 강한 모델은 이 정도 복잡도의 레이스 진단도 스킬 없이 기본으로 통과한다는 뜻입니다. 대신 프로세스 차이는 더 뚜렷해졌습니다. ON 3/3 전부가 자발적으로 systematic-debugging을 호출했고(1차 실험 2/3에서 상승), 셋 다 세션 훅의 “버그 수정 다음에 이 스킬 먼저” 규칙을 근거로 명시했습니다. 비용은 +42.0%로 1차 실험(+43.4%)과 거의 같은 폭이었습니다. 버그가 어려워져도 상대적 오버헤드 비율 자체는 안정적이었습니다.

다만 여기서 다시 의심이 듭니다. 정말 “어려운” 버그였을까요. TOCTOU 레이스는 파일이 두 개로 늘었을 뿐, “클라이언트 체크만으론 부족하고 서버와 DB 계층에 유일성을 강제해야 한다”는 것 자체는 SQLite collation 문제 못지않게 잘 알려진 패턴입니다. systematic-debugging이 실제로 막아주려는 상황은 컴포넌트 개수가 아니라 그럴듯한 오답이 진짜로 유혹적인 경우, 곧 후보 원인이 여럿이라 실험으로 골라내야 하거나 에러 메시지가 엉뚱한 곳을 가리키는 경우에 가깝습니다. 이번에 늘린 축은 “컴포넌트 개수”였지 “정답의 뻔함”이 아니었을 수 있습니다. 그렇다면 6/6이라는 결과는 “스킬이 필요 없다”가 아니라 “이 실험이 여전히 천장 효과 안에 있었다”는 뜻일 수 있습니다.

과정은 진짜였지만, 결과물은 그대로였다

결과물이 같다고 해서 그 과정까지 같았다고 믿으면 안 된다는 것을 이번에 명확히 확인했습니다. OFF 세션은 버그를 그냥 고쳤고, ON 세션은 강제하지 않았는데도 절반 이상이 스스로 절차를 밟았습니다. 이 차이는 diff나 최종 테스트 통과 여부만 봐서는 절대 드러나지 않고, 커밋 로그와 세션 로그를 직접 들여다봐야 보입니다. 앞으로 이런 “프로세스형” 스킬을 평가할 때는 결과물 지표만이 아니라 과정 지표(커밋 분리 여부, 자발적 스킬 호출 여부)를 같이 설계해야 한다는 것을 배웠습니다.

비용 관점의 판단은 조금 더 분명해졌지만, 완전한 결론은 아닙니다. 하루 뒤 일부러 더 어려운 버그로 다시 확인했을 때도 결과는 같았습니다. 프로세스는 더 뚜렷하게 개선됐는데도(자발적 스킬 호출 2/3에서 3/3으로) 그 개선이 결과물 품질로 이어지는 증거는 여전히 없었고, 비용은 두 실험 모두 42~43%로 일관되게 늘었습니다. 두 버그 모두 “컴포넌트는 늘었지만 정답 자체는 잘 알려진 패턴”이었을 가능성이 남아 있어서, 지금 가진 근거로는 정확성을 목적으로 이 대가를 지불할 이유를 찾지 못했다는 정도로만 말할 수 있습니다. 다만 프로세스 자체, 곧 스스로 규칙을 인지하고 근거를 남기고 필요하면 의도적으로 건너뛰는 판단력은 두 실험 모두에서 진짜였습니다. 팀 리뷰나 감사 기록처럼 “과정이 남는 것” 자체에 가치를 두는 상황이라면 판단이 달라질 수 있고, “정답이 뻔하지 않은” 버그를 어떻게 설계할지는 다음 숙제로 남겨둡니다. 지금 제 작업은 그런 목적이 아니라서, 이번엔 비용을 아끼는 쪽을 택합니다.
